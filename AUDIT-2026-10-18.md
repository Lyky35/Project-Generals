# Code Audit Report — 2026-10-18

Scope: whole runtime tree (`GameEngine`, `GameEngineDevice`, `Libraries/WWVegas`,
`Libraries/VulkanRenderer`), with emphasis on the port delta (531 files changed
since the original import `cbcf667`, across 236 commits) and on the bug class
that has produced every game-breaker so far.

## 1. Bug class that matters most: MSVC6 for-scope → GCC UB

Original Generals code was written for MSVC6, where a `for` loop's variable
leaks into the enclosing scope. The port compiles with GCC (C++ for-scope).
Two shapes cause real damage:

- **A. Shadowed redeclaration** — `T x;` followed by `for (T x = ...) {...}`,
  then the outer `x` read after the loop. GCC leaves the outer uninitialized
  (UB; GCC -O3 often folds it to 0 or keeps garbage). Killed the game twice
  already: `TeamsInfoRec::addTeam` (wiped all teams → no reinforcements,
  commit `b7c7687`) and `MeshModelClass::get_deformed_vertices` (infinite loop
  → the frame-74 hang, commit `9374a0c`).
- **B. C++ for-scope leak expectation** — code that reads the loop variable
  after the loop, relying on MSVC6 semantics (`for (int i...) {...} use(i)`).
  Under GCC the read hits a *different* outer variable (or an uninitialized one).

### Method

Custom pattern scanner over the tree (declaration of `x` uninitialized →
`for (T x = ...)` within 60 lines → first post-loop mention is a *read*, not an
assignment/redeclare/next-for). 184 refined candidates in runtime code;
each high-risk hit was then read by hand.

### Confirmed LIVE instances found by this audit (not yet fixed)

1. **`W3DDisplay::calculateTerrainLOD`** —
   `GameEngineDevice/.../W3DDisplay.cpp:1503-1542`
   ```cpp
   Int i;                          // outer, uninitialized
   for (int i = 0; i < NUM_SAMPLES; i++) { ... if (early-out) { i++; break; } }
   frameTime /= ((i) - NUM_TO_DISCARD);   // reads OUTER i under GCC -> UB
   ```
   This is the terrain-LOD auto-calibration. `m_terrainLOD` defaults to
   `TERRAIN_LOD_AUTOMATIC` (`GlobalData.cpp:616`), so it runs at startup.
   Under MSVC6 the average divided by the real sample count; under GCC it
   divides by garbage → terrain LOD chosen essentially at random.
   **Fix:** drop the inner `int`, reuse the outer `i` (and keep the `i++`
   before the early-out `break` correct).

2. **`RoadBufferClass` road insertion** —
   `GameEngineDevice/.../W3DRoadBuffer.cpp:1506-1545`
   ```cpp
   Int i;                          // outer, uninitialized
   for (int i = 0; i < m_numRoads; i++) { ... break; }   // leaves INNER i
   ...
   Int addIndex = i;               // reads OUTER i under GCC -> UB
   if (addAfter) addIndex++;
   ```
   The insertion index for a new road segment is garbage → out-of-bounds or
   wrong-position writes into the road array whenever two adjacent segments
   merge/split (tank tracks & scorch-road network updates).
   **Fix:** same — un-shadow the loop variable.

3. **`ScriptEngine` counter/flag lookup** —
   `GameEngine/.../ScriptEngine.cpp:5431-5456` and `5569+` — same shadow shape
   *but* the outer is assigned before use (`i = m_numCounters; return i;`),
   so it is currently benign. Worth un-shadowing anyway to keep the pattern
   rare.

Everything else in the 184-hit list that was inspected is a **false positive**
(outer variable dead; every later use inside a re-declaring loop). The
remaining untriaged tail is mostly the same benign shape.

### Remediation plan for this class (how I would proceed)

- Mechanical sweep of the confirmed + borderline list: change
  `for (int x = ...)` → `for (x = ...)` where an outer `x` exists, or rename
  the inner loop variable. ~30-50 one-line edits, zero behaviour change on
  MSVC, fixes UB under GCC.
- Add `-Wshadow` to the release build *as a warning*, triaged down over time.
  A warning build with `-Wshadow -Wmisleading-indentation` was started; it
  produced 135 shadow warnings in the first 9% of the tree before failing in
  `VulkanRenderer` (its CMake targets treat warnings as errors — exclude or
  relax that target for audit builds). Every `declaration of 'i' shadows a
  previous local` in GameEngine/GameEngineDevice/WWVegas deserves the same
  manual pass as above; WPAudio/Compression/Tools hits are lower priority
  (Tools are not in the RTS binary at all).
- Keep the existing safety nets (`mesh==NULL` break in the skin flush,
  poly-list cycle guard) — they turned silent hangs into survivable frames.

## 2. Port-delta review (531 files)

Reviewed the port's own code and the three recent research passes. Known
defects / debts, in rough severity order:

### Correctness bugs worth fixing

1. **`VulkanMapTexOp` collapses** (`dx8wrapper.cpp:2683-2713`):
   `DOTPRODUCT3`, `MODULATE2X/4X`, `BUMPENVMAP*` all degrade to plain
   `MODULATE`; `SELECTARG1` with `ARG1=DIFFUSE/CURRENT` disables the stage
   entirely. Affects specular/bump-ish materials (brightness, not geometry).
   *Fix:* implement the missing ops in `mesh.frag` + spec constants, or map
   `SELECTARG1(DIFFUSE)` to the existing SELECTARG2-style op instead of
   disabling the stage.
2. **`D3DTSS_TEXTURETRANSFORMFLAGS` is never read** — projected texture
   transforms (`D3DTTFF_PROJECTED|COUNT3`) are treated as plain 2D. Only
   matters for perspective texgen mappers (rare in Generals assets).
3. **Matrix-mapper stage mismatch** (`matrixmapper.cpp:218-257`): sets
   `TEXCOORDINDEX` on the *UV array slot* but the texture matrix on
   `D3DTS_TEXTURE0+Stage`; when `UVSource[stage] != stage` the matrix write
   lands on a stage ≥2 and is dropped (`dx8wrapper.h:720-725`).
4. **`vertmaterial.cpp:861-868`**: `W3DVERTMAT_STAGE0_MAPPING_BUMPENV` case
   sits inside the *stage-1* switch (dead code) — stage-0 bump-env materials
   never receive a mapper.
5. **DDS stubs**: `textureloader.cpp:245-274` `Load_Compressed_Texture`
   creates an *empty* VkTexture ("TODO: upload each DDS level"); a DDS that
   takes this path renders as undefined/black. `ddsfile.cpp:292-295`
   `Copy_Level_To_Surface(IDirect3DSurface8*)` is a no-op (the memory
   overload works and is the live path). `surfaceclass.cpp` file ctor makes a
   blank 64×64. Low priority while no DDS takes these paths, but they are
   silent-black generators.
6. **Skin FVF has only 2 UV channels** (`dx8renderer.cpp:669-671` forces
   `dynamic_fvf_type`): translucent meshes that also carry a lightmap on UV
   slot ≥2 lose it through the sorting path. Opaque rigid meshes now bind
   slots 0-3 (fixed today); this remains a known limit for *translucent*
   lightmapped surfaces.
7. **Legacy no-op stubs** (`dx8wrapper.cpp:3111-3135`): `Set_StreamSource`,
   `Set_BlendFunc`, `Set_Lighting`, stencil setters — only shadow code calls
   them today; fine, but any future caller gets silent no-ops.

### Intentional / documented (no action)

- `DoShadows` hard-off (`W3DShadow.cpp:73-83`) — projected/volumetric shadows
  and ground scorch decals deliberately disabled pending a redesign; the
  native shadow-map path replaces unit shadows.
- `DecalSystemClass`/`DecalMeshClass` have zero callers (dead upstream code).
- Point sprites are not used anywhere; WW3D expands particles to quads on the
  CPU (verified while fixing FX).

## 3. Repo hygiene: case-variant triplicates

Many sources exist three times (`Foo.cpp`, `foo.cpp` -> symlink,
`FOO.CPP` -> symlink). Git tracks all three names; CMake references one.
This already bit this session: a `git add` of the lowercase alias silently
missed the real file and produced an incomplete commit (fixed by a follow-up
commit). **Remediation:** `git rm` the symlink entries, keep one canonical
casing per file, add `.gitattributes`/CI check to reject case-only duplicates.
